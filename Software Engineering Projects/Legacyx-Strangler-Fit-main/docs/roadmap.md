## Phase status

- [x] **Phase 1 — Legacy monolith**: all six domains, EF Core + PostgreSQL. Written, not build-verified here (NuGet blocked) — see `legacy-monolith/README.md`.
- [x] **Phase 2 — Gateway**: routing, rollback, health. Zero dependencies — actually built, run, and live-tested here, including one real bug found and fixed. See `gateway/README.md`.
- [x] **Phase 3 — Customer extraction**: Spring Boot, own database. Written, not build-verified here (Maven Central blocked) — see `services/customer-service/README.md`.
- [x] **Phase 4 — Database migration**: Python script. Actually run end-to-end against real Postgres — dry run, real run, idempotent re-run, all verified. See `migration/data-migrator/README.md`.
- [x] **Phase 5 — Order extraction**: ASP.NET Core, own `order_db`, wired into the gateway's routing table (verified: independent toggle, doesn't affect Customer's routing), migration script verified with real FK resolution (CustomerId→CustomerNo, ProductId→Sku). Service itself written but not build-verified here (NuGet blocked) — see `services/order-service/README.md`.
- [x] **Phase 6 — Kafka**: real broker in `docker-compose.yml` (KRaft mode), transactional outbox in Order Service (`OutboxMessage` + `OutboxPublisher`), `notification-service` consumer. Event contract in `docs/architecture/event-architecture.md`. The consumer's business logic is genuinely tested (`services/notification-service/test_handle_event.py`, no broker needed) and caught a real dependency bug (`kafka-python` → `confluent-kafka` swap) before it became a problem. The actual network path (producer → Kafka → consumer) needs Docker, which this sandbox doesn't have — see `MANUAL.md`.
- [x] **Phase 7 — Inventory extraction**: Spring Boot, own `inventory_db`, wired into the gateway (verified: routes independently of customer/order). Also consumes `OrderCreated` via Kafka to auto-reserve stock — a second, independent consumer alongside notification-service, added with zero changes to Order Service. Migration script verified with real data. Service itself written but not build-verified here (Maven Central blocked) — see `services/inventory-service/README.md` and `MANUAL.md`.
- [x] **Phase 8 — Resilience**: hand-rolled circuit breaker + timeout + idempotent-only retry in the gateway (see `docs/architecture/resilience.md` for why hand-rolled, not Polly) — fully live-tested: killed a real backend mid-test, watched the circuit open, fail fast (9ms vs ~615ms), recover via half-open, and confirmed POST never retries. Spring Kafka's `DefaultErrorHandler` added to inventory-service's consumer for message-processing retries (not live-tested — Maven Central blocked, same as the rest of that service).
- [x] **Phase 9 — Observability**: correlation IDs generated/propagated/logged across every service (gateway, legacy-monolith, order-service, customer-service, inventory-service), Prometheus metrics on all four modern-side services (gateway: hand-rolled; order-service: prometheus-net; customer/inventory-service: Micrometer), Prometheus + Grafana + Loki in `docker-compose.yml` with Grafana datasources auto-provisioned. Correlation IDs instead of full OpenTelemetry SDK — see `docs/architecture/observability.md` for why. Gateway's correlation handling and `/metrics` output live-tested; the rest needs Docker to verify (`MANUAL.md`). No Loki log shipping and no Grafana dashboards yet — flagged as real gaps in the doc, not hidden.
- [x] **Phase 10 — Security**: JWT auth (hand-rolled HS256, no library, same dependency-free reasoning as the rest of the gateway) + RBAC (ADMIN/MIGRATION_ENGINEER/OPERATOR) gating the gateway's admin endpoints — the spec's explicit requirement ("migration configuration changes must require an authorized role"). PBKDF2 password hashing, no hardcoded credentials anywhere, rate-limited login, and an audit log matching the spec's example format. Fully live-tested: 8-step flow covering 401 vs 403, role enforcement, audit trail accuracy, and rate limiting — all passed, one real bug (401/403 conflation) found and fixed during testing. Business-API traffic itself is *not* auth-gated — documented as a deliberate scope boundary in `docs/architecture/security.md`, not hidden.
- [x] **Phase 11 — Dashboard**: Next.js 16, TypeScript, plain CSS. Login, per-domain routing control (cutover/rollback buttons, role-gated to match the gateway's own RBAC exactly), circuit breaker status, ADMIN-only audit log. `npm install`/`npm run build` genuinely run here — real dependency vulnerabilities (PostCSS/sharp CVEs at Next 15) found and fixed by upgrading to Next 16, not shipped. Server-rendering and both routes confirmed serving valid HTML; the actual interactive/client-hydrated behavior needs a real browser to verify (documented honestly in `dashboard/README.md`, not glossed over) — see `MANUAL.md`.
- [x] **Phase 12 — Testing + load testing**: 20 real, passing pytest tests (`migration/data-migrator/` ×17, `services/notification-service/` ×3) — unit tests for all three migration transform functions plus integration tests against a real throwaway Postgres database. One representative xUnit file (legacy-monolith) and one JUnit file (customer-service) written to the correct pattern, unverified here (NuGet/Maven Central). k6 installed and run for real (downloaded from GitHub releases, no apt package) — one clean result captured (1,280 requests, 252.7 req/s, 0% failures); the full 100/500/1,000-VU matrix wasn't completed due to genuine, documented sandbox process-management flakiness rather than a script or methodology problem. See `docs/architecture/testing.md` and `docs/architecture/load-testing.md`.
- [x] **Phase 13 — Documentation**: all 9 architecture docs the spec names now exist (`overview`, `legacy-architecture`, `modern-architecture`, `migration-architecture`, `data-architecture`, `event-architecture`, `security`, `observability`, `disaster-recovery`), plus three not in the original list but written along the way (`resilience`, `testing`, `load-testing`) and a full threat model covering all 12 named threats. ADR-004 (Java+.NET) and ADR-005 (Kafka) written; **ADR-006 through ADR-010 explicitly skipped on request** — the topics they'd cover (separate databases, API gateway, anti-corruption layer, outbox pattern, Docker Compose over Kubernetes) are already substantively covered in the architecture docs above, just not in formal ADR format.

## Known issues carried forward

- **Cross-domain customer references**: partially addressed by Phase 5's design (Order references customers by `customerNo`, not a numeric ID, so it doesn't care which database currently owns the customer) — but Order Service doesn't yet *validate* a `customerNo` against either system at creation time. Real fix: Order Service asks the gateway to resolve it, since the gateway already knows which backend currently owns Customer. See `services/order-service/README.md`.
- Same pattern will apply to Inventory once Phase 7 lands: Order references products by `Sku`, not a numeric ID, for the same reason.
