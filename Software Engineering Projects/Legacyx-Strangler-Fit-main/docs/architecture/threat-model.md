# Threat model

Each threat below is assessed against what's actually built, not generic security theory — several of these have real, already-documented mitigations from earlier phases; a few are genuine, undefended gaps, stated as such rather than hand-waved.

| Threat | Impact | Likelihood | Mitigation | Residual risk |
|---|---|---|---|---|
| **Unauthorized migration** (someone flips a domain to modern/legacy without permission) | High — could route real traffic to an unready or compromised backend | Low | JWT + RBAC on `PUT /admin/routing/{domain}` (ADMIN/MIGRATION_ENGINEER only), audit-logged. Live-tested (`docs/architecture/security.md`). | Audit log is in-memory, not write-once persisted — an attacker with ADMIN access could act and the trail would survive only until restart. |
| **Routing manipulation** (tampering with the routing table directly, bypassing the API) | High | Very low | `RoutingState` is in-process memory, not exposed by any other endpoint or shared store — there's no separate attack surface to manipulate it *besides* the authenticated API. | If the gateway process is compromised at the OS level, in-memory state offers no protection — true of most in-memory state generally. |
| **Credential theft** (a JWT or password is exfiltrated) | High — full admin access until expiry | Low–medium | Passwords are PBKDF2-hashed (never stored/logged in plaintext); JWTs expire after 1 hour with no refresh; rate limiting slows brute-force guessing. | No token revocation — a stolen *valid* JWT works until it naturally expires; no mechanism to invalidate it early. |
| **JWT compromise** (forging or tampering with a token) | High | Very low | HMAC-SHA256 signature, constant-time comparison (`CryptographicOperations.FixedTimeEquals`) to prevent timing attacks, secret required via env var with no hardcoded fallback. | Single shared secret across all tokens — compromise of the secret compromises every issued and future token until it's rotated (which requires a restart with a new `JWT_SECRET`). |
| **API abuse** (flooding an endpoint) | Medium | Medium | Rate limiting on `/auth/login` specifically (5/min). | No rate limiting on the business API traffic the gateway forwards, or on the other admin GET endpoints — someone with a valid token could still hammer `/admin/routing` repeatedly. |
| **SQL injection** | High if present | Low | All database access across every service uses parameterized queries / an ORM (EF Core, Hibernate, or parameterized `psycopg2` calls in the migrators) — no raw string-concatenated SQL anywhere in this codebase. | Not independently audited by a separate tool (e.g. static analysis) — this is a claim based on how the code was written, not a scan result. |
| **Broken authorization** (a role doing something it shouldn't) | High | Low | Explicit role allow-lists per endpoint (`docs/architecture/security.md`'s table), tested live for exactly this — OPERATOR correctly blocked from writes, MIGRATION_ENGINEER correctly blocked from the audit log. | Business-API traffic (customer/order/inventory CRUD) has no authorization at all — anyone who can reach the gateway can use it. Documented as a deliberate scope boundary, not fixed. |
| **Event tampering** (forging a Kafka message) | Medium | Low (requires network access to Kafka) | Kafka itself has no authentication configured (`docker-compose.yml`'s KRaft setup is plaintext, no SASL/ACLs) — anyone who can reach the broker can publish to `legacyx.orders`. | Real gap: no message-level signing, no broker-level access control. Acceptable for a local demo, not for a real deployment. |
| **Sensitive log exposure** | Medium | Low | Structured logs include correlation IDs, method/path/status/timing — never passwords, tokens, or full request bodies. | Not automatically enforced (no log-scrubbing middleware) — relies on every log statement having been written carefully, which is a process guarantee, not a technical one. |
| **Service impersonation** (a rogue process pretending to be a backend) | Medium | Low (requires network access inside the Docker network) | Services communicate over the Docker Compose internal network by hostname; nothing external can reach `legacy-monolith:8080` etc. directly without exposing that port. | No mTLS or service identity verification between the gateway and its backends — anything that can reach the internal network is trusted implicitly. |
| **Replay attacks** (resending a captured request) | Medium | Low | JWTs are time-limited (1 hour). Idempotent methods (GET/PUT/DELETE) are safe to replay by definition; POST is never auto-retried by the gateway specifically to limit accidental replay (`docs/architecture/resilience.md`). | No nonce or request-ID deduplication — a captured, valid POST request *could* be manually replayed by an attacker within the token's lifetime and would succeed again. |
| **Data corruption** (migration writes bad data) | High | Low | Every migration script validates row counts and spot-checks migrated fields against the source after running, and is idempotent (verified live — re-running never duplicates). Transactional outbox ensures an order and its event can't drift apart. | No rollback-of-migration capability — if a migration *did* write bad data, there's no automated "undo," only manual cleanup. |

## What this threat model doesn't cover

Infrastructure-level threats (host compromise, Docker daemon security, dependency supply-chain attacks beyond the CVE check already done for the dashboard in `dashboard/README.md`) are out of scope here — this is an application-level threat model for what this project's own code controls, not a full deployment security review.
